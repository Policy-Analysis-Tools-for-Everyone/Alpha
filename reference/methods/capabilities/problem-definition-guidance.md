# Writing Policy Problem Statements — Agent Guidance (Bardach)

> **Source:** Distilled from Eugene Bardach, *A Practical Guide for Policy Analysis: The Eightfold Path to More Effective Problem Solving*, “Step One: Define the Problem.” **Provenance note:** Derived from the edition supplied (“Version 4”, not the latest 6th edition). The problem-definition guidance is stable across editions, but if you have access to the 6th edition, reconcile any wording differences before treating this as canonical. **Purpose:** Operating instructions for an agent that helps a user *draft, critique, and sharpen policy problem statements*. This is not a summary of the book — it is a checklist + rubric + examples for producing good problem statements.

## How to use this document

When asked to write or improve a problem statement:

1.  **Draft** using the *Drafting scaffold* below.
2.  **Pressure-test** the draft against the *Core rules* (each rule is a pass/fail gate).
3.  **Score** the draft against the *Self-check rubric* and revise until it passes every “must” criterion.
4.  **Offer one or two variants** when the framing is genuinely contestable (e.g., the problem could be defined around a condition *or* its cause). Defining the problem is iterative — present the trade-off rather than silently picking one.

A good problem statement is **one or two sentences**, evaluative, quantified where possible, free of any hidden solution, and free of unexamined causal claims.

## Core rules (each is a gate the draft must pass)

### 1. Frame as a deficit or an excess

Most substantive problems can be cast as *too much* or *too little* of something. Use the word **“too”** deliberately — “too big,” “too small,” “growing too fast,” “growing too slowly.”

- Include the **future tense** where relevant: problems worth attention often aren’t here yet but are in prospect (“…growing by 140,000 per year, faster than we can build capacity”).
- **Exception — do not force deficit/excess framing** when the task is already a *well-structured decision* (“dump the spoils in the Bay or the Pacific”) or a *pure invention* challenge (“find grant funds to close the gap”). Those are problems for the analyst, but not the substantive condition-type problem this framing serves.

### 2. Make it evaluative — justify why it is a *public* problem

A “problem” asserts something is *wrong*, and “wrong” is contestable. State, at least implicitly, why this condition legitimately warrants public resources. Bardach’s primary lens is **market failure** — a public case is strongest when the condition stems from one of:

- Hard to collect payment from all beneficiaries (positive externalities, e.g. basic science).
- Beneficiaries don’t bear the true cost of consumption (negative externalities, e.g. emissions using clean air as a sink).
- Buyers/sellers can’t know true quality (information asymmetry, e.g. repair services, medicine).
- Marginal cost below average cost over the demand range (natural monopoly / near-zero-marginal-cost goods).

Beyond market failure, legitimate public problems also include: **breakdown of non-market systems** (e.g. families), **low living standards arising precisely because markets work** and don’t reward those lacking marketable skills, **discrimination** against minorities, and **government failing in roles it is expected to fill** (e.g. public schooling). \> If you cannot locate the problem in *some* such justification, flag that the “problem” may not be one a public intervention can or should address.

### 3. Quantify if at all possible — attach magnitudes

Every assertion of deficit/excess should carry a number. How big is “too big”? Replace adjectives with magnitudes.

- A point estimate plus a **range** is often best: *“~250,000 homeless persons in families, plausibly 100,000–400,000.”*
- If you can’t produce a number, at minimum **name the metric** that *would* measure it — this makes the definition concrete and behavioural. Prefer *“too many people with incomes over £60,000 in subsidised housing”* to *“too many well-off people in public housing.”*
- Where the data don’t yet exist, say so and note what evidence would calibrate it (don’t fabricate figures — use a clearly marked placeholder).

### 4. Diagnose causal conditions — but only with care

You may define a *cause* of trouble as the problem itself (“states won’t enforce engine maintenance” as a cause of air pollution). This is powerful because it points toward action — but it is **diagnostic, not merely descriptive**: it smuggles in a causal claim. The word “definition” can make that claim escape scrutiny.

- Only frame a cause as the problem if you have evaluated the causal chain and believe it is **real, not assumed**.

### 5. Use “the odds” for risk and uncertainty

When the problem is probabilistic, state it that way: *“The odds are too high that this reactor suffers a radiation-emitting accident in the next 25 years.”* “The odds” is the right locution for anything resistant to quantification, and it also works for criteria (“maximise the odds that…”).

### 6. Look for latent opportunities, not just troubles

A missed opportunity is a legitimate problem. Don’t let a “what’s broken” frame crowd out improvements no one has complained about. Generic opportunity sources worth scanning: operations-research gains (sequencing, matching, clustering), cost-based pricing, by-products of personal aspirations, complementarity, input substitution, developmental sequencing, exchange, multiple-function design, non-traditional participants, and underutilised capacity.

## Anti-patterns (reject the draft if it does either)

### Pitfall A — Defining the solution into the problem

The statement must **not** contain an implicit solution. Keep it a stripped-down description and leave the search for solutions open.

- **Tip-off:** if you catch yourself thinking *“Aha, but that’s not the* real *problem…“*, you’ve probably smuggled a solution in.

| Don’t say (hidden solution)                          | Why it’s wrong                                                         | Try instead                                                                |
|------------------------------------------------------|------------------------------------------------------------------------|----------------------------------------------------------------------------|
| “There is too little shelter for homeless families.” | Pre-commits to “build more shelter”; blocks prevention.                | “Too many families are homeless.”                                          |
| “New schools are being built too slowly.”            | Pre-commits to “build more schools”; blocks reuse / distance learning. | “There are too many schoolchildren relative to available classroom space.” |

### Pitfall B — Swallowing the causal claim in a diagnostic definition

If the definition rests on a cause-and-effect assertion (“too much cocaine use” → assumes it causes crime, ill-health, etc.), **the causal link must be evaluated, not assumed.** Ask: does X actually lead to the bad outcomes, and to what degree? Withhold the framing until the evidence supports it.

## Drafting scaffold

Work through these in order; the output is the bracketed final line.

1.  **Issue rhetoric → raw material.** Start from the client’s / debate’s language (“teenage pregnancy,” “global warming”), but *don’t echo it*. Treat it as raw material; get past partisan or ideological loading to something analytically manageable.
2.  **Pick the primary focus.** A label may encode several problems (“teenage pregnancy” = morality / life-chances / taxpayer cost / social disintegration). Choose one primary focus to keep the analysis bounded; define a second only if it’s simple enough.
3.  **Cast as deficit / excess** (Rule 1) — insert “too.”
4.  **Attach a magnitude** (Rule 3) — number, or a range, or at least a named metric.
5.  **Anchor the evaluative basis** (Rule 2) — be ready to say *why* it’s a public problem.
6.  **Strip out any implied solution** (Pitfall A).
7.  **Surface and check any causal claim** (Rule 4 / Pitfall B).

→ **Final statement (1–2 sentences):** `[deficit/excess] + [quantified magnitude or metric] + [affected population/scope] + [time horizon if relevant]`, with no embedded solution and no unverified causal claim.

## Self-check rubric

Before returning a problem statement, confirm:

**Must pass (block on any failure):**

- States a deficit or excess (or is a legitimate decision/invention/opportunity exception).


- Contains **no implicit solution** (passes the “that’s not the real problem” test).


- Any causal claim is flagged as a claim, not asserted as fact.


- Length is ~1–2 sentences; it describes a condition, not a programme.

**Should pass (note the gap if missing):**

- Carries a magnitude — number, range, or at minimum a named metric (no fabricated figures; placeholders marked).


- Has an articulable evaluative basis (market failure or another legitimate public-problem category).


- Time horizon stated where the problem is prospective.


- Risk/uncertainty expressed via “the odds” where applicable.

**Process reminder:**

- Treated as **iterative** — flagged that the definition may be re-sculpted as evidence and ruled-out alternatives accumulate, and (in an office context) negotiated with colleagues/superiors.

## One-line reference

> A good policy problem statement names a **quantified deficit or excess** affecting a defined population over a defined time, rests on a **defensible reason it’s a public problem**, contains **no hidden solution and no unverified cause**, and is held **provisionally** for iteration.
